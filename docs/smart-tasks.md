# 智能任务

在 Web 控制台打开 **智能任务**，配置固定提示词、模型、允许的 MCP 服务器、收件目标和排程。AI 在后台自主完成工具调用，最终结果**不经人工审核**直接投递。仅有 Web 管理员能操作，不提供 Telegram 用户建任务命令。

## 首次配置

1. 在 **AI 配置** 中保存支持工具调用的文本模型。任务可单独选择模型，或跟随全局任务模型（未选全局任务模型时沿用聊天模型）。运行时所选模型不存在或不支持工具会明确失败，不偷偷更换模型。
2. 开启 MCP 总开关，配置并启用需要的服务器，为服务器开启 **允许后台任务使用**（旧配置和新服务器均默认关闭）。
3. 新建智能任务，填写名称和提示词，按服务器多选工具。选中服务器意味着开放该服务器 `allowed_tools` 所允许的全部工具，不绕过服务器自身工具白名单。
4. 明确填写 Telegram 聊天 ID 或 `@channel`，多个用逗号分隔；可显式导入热点推送目标，不默认广播。最多100个目标。可另填单个失败通知目标。
5. 选择排程并保存。暂停的任务仍可手动运行；选中「启用自动排程」后保存，会在确认提示后按排程自动运行。

系统向模型提供当前北京时间，但不提供其他运行结果或聊天记录。每次独立执行；需要“仅变化时通知”的任务必须自行通过允许的工具获得判断所需信息。

**权限提醒：**后台运行使用独立系统权限，不借用 Telegram 管理员 ID，也不受聊天用户白名单授权。每个运行的连接和工具分发表独立，只能看到选定服务器；全局开关、服务器启用状态、后台授权和服务器配置在调用前重新检查。任一选定服务器不可用或没有允许的工具时，不静默少带工具继续执行。

工具结果被作为不可信数据处理，但提示词不能保证消除提示注入。服务器若具备发信、写文件等能力，试运行和正式运行都可能执行这些真实操作。请选择可信服务器；关闭服务器后台授权可阻止后续调用，但不能撤销已经发出的工具请求。

## 排程与手动触发

时间统一为 **Asia/Shanghai（北京时间）**，不随浏览器和服务器时区变化。

| 类型 | 规则 |
| --- | --- |
| 仅手动运行 | 保存后不自动执行，随时点击「立即运行并投递」 |
| 一次性定点 | 指定未来北京时间，自动执行一次 |
| 每日定点 | 每日1至24个 `HH:MM` 时刻 |
| 每周定点 | 选择多个星期与一个 `HH:MM` 时刻 |
| 固定间隔 | 每5至525600分钟，保存或启用时重新建立时间锚点 |

间隔按计划时间推进，不随上次耗时漂移。手动运行和试运行不改变排程。编辑只影响之后创建的运行；已排队或已执行的运行使用冻结的任务定义。暂停不撤销已排队/执行的运行；删除停止未来触发并跳过未开始的排队运行，已执行的运行继续，历史记录仍保留。

一次性任务如果已经完成/错过，编辑其他字段或重新启用不会重新执行过去的时刻；需要重设未来时间或手动运行。多个页面并发修改会产生版本冲突，旧页面不能静默覆盖。

## 运行与限制

- 全局最多2个正在执行（包括结果投递阶段）的运行；同一智能任务不重叠，试运行也计入。
- 上一次仍在排队或执行时，新触发记为「已跳过」。其他任务排队超过10分钟也跳过。
- 默认最多8轮、16次工具调用、600秒 AI 与结果准备时间；可配置至40轮、50次、1800秒。单工具调用超时和结果长度仍受全局 MCP 设置约束。Telegram 投递沿用单次网络请求超时及事务日志，不用 AI 超时强行重发消息。
- 模型错误、工具失败/不可用、输出不完整、超限或超时：不投递部分 AI 结果，不自动再次调用模型。
- 结果最多100000字符，支持现有 Markdown 子集，长文分段；最多4张 MCP 图片，安全下载并转为私有素材后投递。无文字但有有效图片可成功。
- 若提示词设定的通知条件不满足，模型应仅返回 `[[SMART_TASK_NO_PUSH]]`，运行记为「无需推送」。其他内容（包括空结果）不会被默认为该状态；空文字且无图片会失败。

失败通知只包含运行标识与简短原因，不附工具参数、结果或上游凭证。失败通知本身也有投递日志，不会因通知失败再次发通知。试运行失败不发送正式失败通知。

## 试运行和记录

先保存任务，然后点击 **试运行已保存任务**：
- 试发目标留空：真实执行模型和工具，只在 Web 展示结果及图片，不投递。
- 填单个测试目标：仅投递到该测试目标，不使用正式收件目标。

记录包含冻结的任务定义、实际模型、结果与图片、开始/结束时间、工具调用名称、参数/结果摘要及耗时。工具摘要会遮蔽配置中的密钥以及常见敏感字段，最多2000字符，不保存模型思考链。模型返回用量时逐轮累加；未返回时显示“模型未返回”，不估算费用。

每个智能任务同时保留**最近50次**和**最近7天**内的运行，取保留范围的并集；未完成运行及仍有投递工作的记录不清理。低频或已删除任务的最近50次可能长期保留。配图、结果投递与失败通知日志随运行统一清理；不是管理员推送的三天保留期。

## 投递失败和重启

结果与投递安排在同一 SQLite 事务中保存，然后由已有推送执行器发送。投递过程先记录发送尝试，再执行 Telegram 请求：
- 明确失败：可勾选失败部分手动重试，不再调用 AI。恢复前置失败后，会继续首次发送该目标后续未尝试的部分。
- 结果不明：可能已被 Telegram 接收，不自动重发，也不允许把它选作失败重试。
- 各目标独立，一个目标失败不会阻止其他目标。

重启时：
- AI 尚未完成的运行标为中断，不自动重跑。
- 已进入投递的运行按原有逐部分日志恢复，成功部分不重发。
- 一次性排程延误不超过30分钟可补跑，超过记为已错过。
- 周期排程停机漏掉的不补，仅推进到下一次；正常运行时超过60秒的调度延误也记为错过，不突发追赶历史排程。

## 部署和测试

智能任务与管理员推送共用 `data/admin_push/push.sqlite3` 及其私有素材目录，沿用现有持久数据挂载，不增加 Redis/队列依赖。必须是单实例机器人；备份/迁移应先停机，再整体备份 `data/admin_push/`。独立启动 Web 只能编辑，运行需要正常机器人启动器和 Telegram 客户端就绪。

后端与浏览器测试使用临时 SQLite、假模型、假 MCP 与假 Telegram，不调用生产服务：

```bash
python -m unittest discover -s tests -p 'test_smart_tasks*.py'
```

浏览器测试需要 Playwright 及本机 Chrome（或设置 `PLAYWRIGHT_CHANNEL`）。Playwright 仅是测试依赖，不加入生产依赖。
